## Blocking

### B1. `--sequential` loads a whole-genome index 4+ times per call

`label_call` calls `aligner.hits(alt)` and `aligner.hits(ref)`. `hits()` calls `hits_on("hap1")` then `hits_on("hap2")`, and `ensure()` clears the other index each time. So every call loads hap1, hap2, hap1, hap2, plus more for each tolerant `mid` shift.

Measured with a counter on `mappy.Aligner`: 10 calls → **2 loads joint, 40 loads sequential**. On a whole-genome `.mmi` each load is tens of seconds (minutes if it builds from FASTA), so a sample with thousands of calls would take days. The test only checks that labels match, so it passes.

Fix — two passes, as PRODUCTION_PLAN §3.2 describes:

1. Build every query for every call first (alt, ref, and each tolerant-shift alt), keyed by `(row_index, query_id)`.
2. Load hap1, map all queries, keep the `Hit`s, free the index.
3. Load hap2, map all queries, free it.
4. Decide each label from the stored hits with the existing `_group_hits` / `_passes` logic.

Split `label_call` into `queries_for(row)` and `decide(row, hits)` so joint and sequential modes share the decision code. Add a test that monkeypatches `mappy.Aligner` with a counter and asserts **exactly 2 loads** for N calls in sequential mode, alongside the existing "labels identical" test.

### B2. `absorb_nearby_drp_breakpoints` removes real breakpoints

With `max_distance = insert_median` (399 here), any DRP-only interval within ~400 bp of a clip-supported one is merged into it. For events shorter than the insert size, the DRP-only interval is often the **other end of the same event**. Traces from the large pilot (input → output of the absorb step):

| Truth | Before absorb | After absorb | Result |
|:--|:--|:--|:--|
| DEL HET 536580–536880 | `[536575–536643, clip 536580]`, `[536794–536885, DRP-only]` | one interval `536575–536885` | both ends merged → **no call** (was label 1) |
| inv.del HET 243900–244200 | `[243779–243921, clip]`, `[243974–244055, DRP-only]`, `[244153–244306, clip]` | middle interval merged into the first | inv.del → plain INV, **label 0** (was 1) |
| inv.del HOM 1951200–1951500 | `[1951096–1951141, DRP-only]`, `[1951195–1951232, clip]`, … | spurious interval merged (intended) | extra 82 bp block gone, but call is now `ABD` DEL HET; still label 0 |

So the step fixed the one case it targeted and broke two correct calls. Distance can't separate them: the spurious interval is 54 bp from its anchor, the real one in the inv.del is 53 bp away.

Evidence that does separate them:

- **Single soft clip inside the interval.** `243974–244055` contains a lone clip at 244050 (the later stamping step sets it, so the final table shows `clip`). `536794–536885` has one at 536880. The spurious `1951096–1951141` has none. Absorb runs *before* stamping, so it can't see this. Pass the raw clips in, and never absorb an interval that contains any soft clip.
- **Mate interval of the same DRP cluster.** `cluster_to_intervals` makes the left and right interval of one cluster. The far end of a deletion is the mate of the anchor's cluster. Carry a cluster id on `Breakpoint`, and never absorb an interval into the anchor that shares a cluster with it.
- Also cap the distance well below the event sizes you care about (e.g. ≤ 100 bp, or read length / 2), not the insert size.
- After merging, re-run `merge_breakpoints` so a widened interval can't overlap a neighbour.

Add the three traces above as unit tests (they are small `Breakpoint` lists). Gates for this change: large pilot ≥ 30/32, demo 15x ≥ 34 detected, CI pilot 3/4. If the rule can't meet them, revert the step. Round 11's 82 bp block was a label-0 case in 1 of 32 events; losing whole deletions is worse.

The 1951200 case has a second, separate issue: with the extra block gone it's called `ABD` HET, but truth is inv.del HOM. Check the path and likelihood for this locus after B2. It may be the same short-HOM genotyping problem carried from earlier rounds.

## Should fix before M2

### F1. `fetch_data.py` doesn't match the data sources or the workflow

- **`s3://` is not supported.** It uses `urllib`, but PRODUCTION_PLAN §3.1 says it reads `s3://` in cloud mode. Accept `s3://bucket/key` and either rewrite it to the public HTTPS endpoint (`https://1000genomes.s3.amazonaws.com/<key>`, `https://s3-us-west-2.amazonaws.com/human-pangenomics/<key>`) or call `aws s3 cp --no-sign-request`.
- **No resume**, although the docstring says "Resumes partial downloads". A `.partial` is overwritten from zero. Use an HTTP `Range: bytes=<size>-` request and append. This matters for 15–30 GB CRAMs over home internet.
- **Checksums.** 1KGP publishes MD5s in its index files; HPRC gives MD5/ETags. Requiring SHA-256 means computing it yourself after a trusted download, which defeats the point. Accept `md5:` or `sha256:` prefixed values.
- **Layout mismatch.** It writes `<dest>/samples/<id>/haps/<id>.hap1.fa.gz`, but `label.smk` reads `haps/{sample}.hap1.fa` relative to the run folder. Nothing connects them. Either have `label.smk` read hap paths from `samples.tsv`/config, or have `fetch_data.py` write or symlink the paths the workflow expects. Also note the `.fa.gz` vs `.fa` difference (mappy reads gzip; the rule names should match).
- The placeholder check `"example" in url` would reject any real URL containing that word. Check only for `REPLACE_`.
- `samples.tsv.example` lists HG002 as `female`. HG002 is male (Ashkenazi son). This matters later for chrX/chrY copy-number checks.
- There is no test for a successful download path. Add one with a local `http.server` fixture: fresh, cached, resumed, checksum mismatch.
