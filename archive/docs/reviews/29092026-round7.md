## Findings

### 1. Reverse-strand haplotype hits are rejected (blocker for labels)

`_passes` returns `no_hit` when `hit.strand < 0`, and `label_call` keeps only forward hits.

- Assembly contigs (hifiasm/HPRC) are not oriented to GRCh38. About half of all contigs are reverse-complemented relative to the reference.
- A true event on a reverse contig is labeled **0**.
- Check: a HOM deletion on a reverse-complemented contig gave `label=0 no_hit`. A HET deletion on a reverse contig gave `label=0 low_identity`.

**Fix:** accept hits on either strand. The paper's criteria (full query coverage, MAPQ ≥ 60, identity > 0.90, no indel ≥ 49 bp) say nothing about strand. `strand` can stay in the output as information.

### 2. Every true HET call is labeled `ambiguous` (blocker; my plan's rule was wrong)

- `LABELS_PLAN.md` section 3 said "alt and ref both pass → NA ambiguous", and the code implements that.
- But for a HET call the other haplotype carries the reference allele, so the ref sequence always passes there.
- Check: a true HET deletion on forward contigs gave `label=NA ambiguous`.

**Fix** (`LABELS_PLAN.md` is corrected):
- `ambiguous` means alt and ref both pass **on the same haplotype**, which happens in a repeat where the aligner can't tell them apart.
- Alt passing on one haplotype and ref on the other is a validated HET event: **label 1**.

With findings 1 and 2, only 1 of 4 true test events (HOM on forward contigs) was labeled correctly. `tests/test_label.py` should add HET and reverse-contig cases, which fail today.

### 3. The reference FASTA is re-read for every call (high)

- `ml-label` passes the `--reference` path into `label_rows`, and `haplotype_sequences` calls `read_fasta(path)` again for each call.
- For GRCh38 that is a read of about 3 GB, then a join into a Python string, for every row.
- **Fix:** open the reference once as an indexed `pysam.FastaFile` (`.fai`), or load only the needed contigs once. Then fetch `chrom:start-end` per call.

### 4. Haplotype index memory (medium)

- Two whole-genome minimap2 indexes are loaded at once, each several GB, and `read_fasta` already holds the reference in memory. That's heavy for a laptop.
- Document the RAM needed.
- Consider labeling one sample at a time, with `--threads 1` for labeling. Or use per-chromosome haplotype subsets when the assembly has chromosome assignments.

### 5. `label.smk` (medium)

- The `call` rule omits the required `-G/--gaps`, so it fails as written.
- Paths are not quoted. The project path has spaces and an apostrophe (`Bao's windows`), so use `{input:q}`, `{output:q}` and quote `config[...]`.
- `samtools` and `minimap2` are called as external tools. The workflow should run inside the container (see `CROSS_PLATFORM.md`), or declare a conda env per rule.

### 6. Carried over

- **Insertions:** the lower-bound flag is still missing for the HOM insertion longer than the fragment (round 6 finding 2).
- **Genotypes:** short HOM duplications are still called HET (documented).
- **Speed:** no chr20 timing, and the Rust kernels are not called.
- **Other:** `filter` is always PASS, and no parity run against the original yet.

## Cross-platform (Windows) summary

`pysam` and `mappy`, and the `samtools` and `minimap2` tools, don't support native Windows. The core caller and training (SAM input, pure Python) do run on Windows, and spawn-mode workers are fine. The single supported full-pipeline runtime should be a **Linux container**, used the same way on Windows (Docker Desktop with the WSL2 backend), macOS and Linux. Details and file-by-file changes are in `docs/CROSS_PLATFORM.md`.
