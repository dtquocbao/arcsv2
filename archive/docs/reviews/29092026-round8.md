## Findings

### 1. The label workflow fails at its first `call` step (high)

- `fetch_region` writes `work/{sample}/{chrom}.bam` with `samtools view -b` and never sorts or indexes it.
- `arcsv2 call --region chr20` reads BAM through `pysam` `fetch(chrom)`, which needs an index. Reproduced: `ValueError: fetch called on bamfile without index`. With an index, the same file loads (9,925 pairs).
- The CI job runs `snakemake -n`, a dry run, so it cannot catch this.

**Fix:**
- `samtools view -u -T ref CRAM chrN | samtools sort -o {output.bam}`, then `samtools index {output.bam}`.
- Declare `{sample}/{chrom}.bam.bai` as an output and as an input of `call`.

### 2. The container runs a stale copy of the code (medium)

- The `Dockerfile` does `pip install "/opt/arcsv2[dev]"`, a non-editable install of the code as it was at build time.
- `arcsv2.ps1` / `arcsv2.sh` mount the repo at `/work`, but the `arcsv2` entrypoint still imports the installed snapshot. After editing code on Windows, the wrapper keeps running the old version until `docker build` is run again.
- The dev container does `pip install -e`, so it is not affected.

**Fix:**
- Add `-e PYTHONPATH=/work/python` in both wrappers and in the CI `docker run` lines. The mounted source then wins.
- Or install editable at `/work` in the image entrypoint.

### 3. No real end-to-end label test (medium; M2 prerequisite)

- `tests/test_label.py` covers `label_call`. The workflow is only dry-run.
- `scripts/simulate_haplotypes.py` already builds both haplotypes. Two small additions give a complete local and CI pilot on simulated data, with no downloads:
  - write them as `hap1.fa` / `hap2.fa`;
  - write the reads as an indexed BAM.
- Run `label.smk` for real, `-j 2`, on a 200 kb simulation in the container job. Assert that `dataset.summary.json` exists and that true events are labeled 1.
- This would have caught finding 1.

### 4. Smaller items (low)

- **CI core job:** install `.[dev,ml,dashboard]`. The dashboard is the one feature meant to run natively on Windows, and today its app test is skipped there.
- **`ml-label --unreliable`:** a configured path that does not exist is silently ignored (`is_file()` check). Error out, or warn, when the option is given but the file is missing, so a wrong path doesn't quietly change labels.
- **`snakemake --use-conda`:** each rule points at the full `environment.yml`. That's fine, but document that inside the container `--use-conda` should be omitted, since the tools are already there.
