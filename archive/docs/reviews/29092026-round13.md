What's good:

- **Two-pass sequential labeling.** `queries_for`, `decide_from_hits` and `decide_row_from_query_hits` split cleanly. Joint and sequential mode share the decision code.
- **The absorb rule is now clip-aware and mate-aware**, capped at 100 bp, and re-merged afterwards. The two correct calls that round 11 broke, the 300 bp deletion at 536580 and the inv.del at 243900, are back to label 1.
- **`fetch_data.py`:** rewrites `s3://` to HTTPS, resumes with Range, accepts MD5 or SHA-256, uses `REPLACE_` as the only placeholder, and has a local HTTP-server test covering fresh / cached / resumed / mismatch. HG002 is now listed as male.
- `make_dashboard_demo.py` prints the scores, so a regression shows up when the demo is rebuilt.

Minor issues to fix in this round:

- **m1. Cluster ids collide across DRP types.** `cluster_id = 0` is reset inside `for kind, group in grouped.items()`, so the first Del cluster and the first Inv cluster both get id 0. `shares_cluster` then treats two unrelated intervals as mates and skips a valid absorb. Use one counter for the whole chromosome.
- **m2. Joint mode now maps every shift query eagerly.** `label_call` builds and maps every `mid` shift candidate before it knows whether the base call validated. That's up to 3 junctions × ~10–30 grid positions × 2 sequences × 2 haplotypes. In round 11 these were only mapped when the base failed. The pilots use mostly `clip` points so it doesn't show there (62 queries both ways), but real data has many `mid` junctions.
  - Joint mode: map `alt`/`ref` first, and build shift queries only when the label is 0.
  - Sequential mode: pass A maps base queries for all rows on hap1 then hap2. Pass B maps shift queries only for rows labeled 0 with a `mid` junction. That's 4 index loads per sample instead of 2, which is fine.
- **m3. The block-length rule can be undone by absorb.** Absorb now runs after `merge_intervals_for_min_block`, so a widened interval can leave a reference block under 50 bp. Run `merge_intervals_for_min_block` again after absorb.
- **m4. Haplotype layout still doesn't meet `label.smk`.** `fetch_data.py` links haps into `<dest>/haps/`, but `label.smk` reads repo-relative `haps/`, `work/`, `results/`, `labels/`. On Windows those sit on the NTFS bind mount, which is slow. Symlinks may also fail there and fall back to copying ~1.8 GB per sample. Fix: add `data_root: /data` to `label.yaml`, and make every rule read and write `{data_root}/haps`, `{data_root}/work`, `{data_root}/results`, `{data_root}/labels`. Keep the pilot configs on `.` so CI is unchanged.
- **m5.** HPRC publishes MD5s in a separate `.md5` file (`<hash>  <name>`), and 1000 Genomes gives no MD5 for `.crai`. Allow `none` for index files (`.crai`, `.fai`, `.gzi`) and record their size instead. Keep checksums required for CRAM, FASTA and assemblies.
- **Carried:** the inv.del HOM at 1951200 is now called `ABD` DEL HET. The spurious block is gone, but the path misses the B′ inversion and the genotype is wrong. Look at it with the short-HOM genotyping item. The other carried items are unchanged from round 12: the HET 3 kb DUP in the CI pilot is never called, `--threads` gives no speedup, and there is no chr20 timing, no parity run against the original ARC-SV, and the filter is always PASS.

## 2. Automatic data download: sources and config generation

Goal: Bao runs one command. It picks samples, writes the config, downloads what's needed, and verifies it. Nothing is edited by hand.

```powershell
.\scripts\arcsv2.ps1 fetch --n-samples 6 --chroms chr20,chr21,chr22            # plan + download
.\scripts\arcsv2.ps1 fetch --n-samples 6 --chroms chr20 --dry-run              # show plan and GB only
.\scripts\arcsv2.ps1 fetch --samples HG00408,HG00438 --chroms chr20
```

(The same flags work as `python scripts/fetch_data.py --auto ...` inside the container.)

### 2.1 Sources (checked 2026-09-29; all public, no account)

| What | Location | Checksums |
|:--|:--|:--|
| 1KGP 30x CRAM list, 2,504 unrelated | `s3://1000genomes/1000G_2504_high_coverage/1000G_2504_high_coverage.sequence.index` | `MD5SUM` column (CRAM) |
| 1KGP 30x CRAM list, 698 related | `s3://1000genomes/1000G_2504_high_coverage/additional_698_related/1000G_698_related_high_coverage.sequence.index` | `MD5SUM` column |
| CRAM object (unrelated) | `s3://1000genomes/1000G_2504_high_coverage/data/{RUN_ID}/{SAMPLE}.final.cram` (+ `.crai`) | from index |
| CRAM object (related) | `s3://1000genomes/1000G_2504_high_coverage/additional_698_related/data/{RUN_ID}/{SAMPLE}.final.cram` (+ `.crai`) | from index |
| Reference (matches the CRAMs) | `s3://1000genomes/technical/reference/GRCh38_reference_genome/GRCh38_full_analysis_set_plus_decoy_hla.fa` (+ `.fai`) | none published; record SHA-256 on first download |
| Centromeres / other regions | same folder, `20150713_location_of_centromeres_and_other_regions.txt` | none |
| HPRC Release 2 assembly list | `https://raw.githubusercontent.com/human-pangenomics/hprc_intermediate_assembly/<PINNED_COMMIT>/data_tables/assemblies_release2_v1.0.index.csv` | pin the commit SHA, record the file MD5 |
| HPRC assembly | `assembly` column, e.g. `s3://human-pangenomics/working/HPRC/HG00408/assemblies/release2/HG00408_pat_hprc_r2_v1.0.1.fa.gz` (+ `.fai`, `.gzi`) | `assembly_md5` column points to a `.md5` file |
| Segmental duplications (unreliable BED, optional) | `https://hgdownload.soe.ucsc.edu/goldenPath/hg38/database/genomicSuperDups.txt.gz` | none |

Format details, verified:

- **1KGP index.** Skip `##` lines. The header line starts with `#ENA_FILE_PATH` and is tab-separated. Use `MD5SUM`, `RUN_ID`, `SAMPLE_NAME`, `POPULATION`. The first column is an ENA `ftp://` path; don't use it. Build the S3 key from `RUN_ID` + `SAMPLE_NAME` as above. Example: `ERR3239480` → `data/ERR3239480/NA12718.final.cram` (15.4 GB, `.crai` 1.4 MB).
- **HPRC CSV** columns: `sample_id, haplotype, phasing, assembly_method, assembly_method_version, assembly_date, assembly_name, source, genbank_accession, assembly_md5, assembly_fai, assembly_gzi, assembly`. There is one row per haplotype. `haplotype` 1 is the paternal (`_pat_`) assembly and 2 is the maternal (`_mat_`) assembly. Map 1 → `hap1` and 2 → `hap2`, and keep only samples with both rows. Each assembly `.fa.gz` is about 0.9 GB.
- **Overlap.** Not every HPRC sample is in the NYGC set; e.g. HG00408 is in the 698-related list and HG00438 isn't in the 2,504 list. Always compute the intersection; never assume it.
- **HTTPS endpoints:** `https://1000genomes.s3.amazonaws.com/<key>` and `https://human-pangenomics.s3.amazonaws.com/<key>`. Both answer bucket listings anonymously. Either host form is fine; keep one per bucket in `S3_HTTPS`.
- **HG002 is not in 1KGP.** Its truth assemblies are at `s3://human-pangenomics/T2T/HG002/assemblies/hg002v1.1.{mat,pat}.fasta.gz`; v1.2 also exists, so pin one. Its short reads are Genome in a Bottle data (`s3://giab/data_indexes/AshkenazimTrio/`) and need downsampling to 30x plus realignment to the reference above. Keep HG002 out of `--auto`. Add it later as a separate `--benchmark hg002` path that runs on HPC.

### 2.2 What `fetch_data.py --auto` does

1. **Catalogs.** Download the two 1KGP indexes and the pinned HPRC CSV into `/data/catalog/`, and record their MD5s in the lock file. Re-running uses the cached copies unless `--refresh-catalog` is given.
2. **Candidates.** Take the samples in both lists that have both HPRC haplotypes, and read the 1KGP `POPULATION` for each.
3. **Selection.**
   - `--samples A,B,...` takes an exact list.
   - `--n-samples N` picks deterministically: sort by population then sample id, then round-robin across populations so the pilot is diverse. `--seed` is a tie-breaker. Print the chosen list.
4. **Check existence.** Send an HTTPS `HEAD` for each CRAM, `.crai` and assembly. Fail early with the sample name on a 404, and print total bytes.
5. **Write config.**
   - `workflows/config/samples.tsv` (generated, gitignored) with the columns `fetch_data.py` already reads. Assembly checksums are read from the `.md5` files; CRAM checksums come from the index.
   - `workflows/config/label.auto.yaml` with:
     - `reference: /data/ref/GRCh38_full_analysis_set_plus_decoy_hla.fa`
     - `gaps`, `unreliable`, `chroms` (from `--chroms`), `samples`
     - `cram: {sample: https://1000genomes.s3.amazonaws.com/...final.cram}`, so `samtools view` streams only the requested chromosomes and picks up `URL.crai` itself
     - `data_root: /data`
     - `sequential: true` (default for laptops; `--no-sequential` to turn off)
   - Both files carry a header comment with the generation time and the catalog MD5s.
6. **Download.** Reference `.fa` + `.fai` (~3.2 GB, once), both assemblies per sample (~1.8 GB per sample), assembly `.fai`/`.gzi`, and the centromere file. CRAMs are streamed by default; download them only with `--fetch-cram` (~15–30 GB each).
7. **Reference BEDs** (new `scripts/make_ref_beds.py`, called by fetch):
   - `gaps.bed` = N-runs in the reference FASTA.
   - `unreliable.bed` = centromeres/other regions from the 1KGP file, plus UCSC segdups when `--segdups` is given.
8. **Lock and summary.** Write `/data/manifest.lock.json` (URL, resolved URL, size, checksum, time, catalog versions). Then print the next command:
   `snakemake -s workflows/label.smk --configfile workflows/config/label.auto.yaml -j 2`.
9. **Safety.** Before downloading, print the plan with the total GB, and stop if free space under `/data` is less than 1.2× that. `--yes` skips the prompt; `--dry-run` never downloads.

Tests (no network in CI):

- Commit tiny fixture snippets of both 1KGP indexes and of the HPRC CSV under `tests/fixtures/catalog/`, 3–5 rows each, including one sample only in 1KGP and one only in HPRC.
- Test: parsing, intersection, the pat/mat → hap1/hap2 mapping, S3 key building for the unrelated and related paths, round-robin selection, and that the generated `label.auto.yaml` loads in `snakemake -n`.
- Add an opt-in `@pytest.mark.network` test that sends a `HEAD` to one real CRAM and one real assembly.

`scripts/arcsv2.ps1 fetch ...` and `arcsv2.sh fetch ...` should map to `python scripts/fetch_data.py --auto ...` inside the container. `arcsv2 fetch` as a CLI subcommand is also fine.

## 3. Docker: its own `arcsv2` project

**Problem.** The wrappers use plain `docker run --rm`, and the devcontainer builds from the Dockerfile directly. So Docker Desktop shows these containers ungrouped or with random names, next to other projects' containers, and `docker compose ls` doesn't list them as a project. Also, `.dockerignore` doesn't exclude `pilot*/`, `haps/`, `labels/`, `results/`, `work/`, `target/` or `ref.fa`. About 175 MB of local test output is copied into the build context, and `COPY .` bakes it into the image.

Fix: one Compose file with a fixed project name, used by the wrappers, the devcontainer and the dashboard.

### 3.1 `compose.yaml` (repo root)

```yaml
name: arcsv2                     # fixed project name, independent of folder or cwd

x-common: &common
  image: arcsv2:dev
  working_dir: /work
  environment:
    PYTHONPATH: /work/python
  volumes:
    - .:/work
    - arcsv2-data:/data
  labels:
    org.arcsv2.role: runtime

services:
  cli:                           # one-off commands: docker compose run --rm cli <args>
    <<: *common
    build: { context: ., dockerfile: Dockerfile }
    profiles: ["cli"]

  dashboard:                     # docker compose up dashboard
    <<: *common
    container_name: arcsv2-dashboard
    command: ["dashboard", "--results", "/work/results", "--host", "0.0.0.0"]
    ports: ["8501:8501"]
    profiles: ["dashboard"]

  dev:                           # Cursor / VS Code devcontainer
    <<: *common
    container_name: arcsv2-dev
    entrypoint: ["sleep", "infinity"]
    profiles: ["dev"]

volumes:
  arcsv2-data:
    name: arcsv2-data            # same volume name the wrappers already use
```

For a host data folder instead of the named volume, add a `compose.override.yaml` example (gitignored) that remaps `/data` to a local path, e.g. `D:/arcsv2-data:/data`, and explain it in CROSS_PLATFORM.md. Don't keep the `ARCSV2_DATA` env-var switch: Compose can't fall back between a named volume and a host path cleanly.

### 3.2 Wrappers

`scripts/arcsv2.sh` and `scripts/arcsv2.ps1` should call Compose with an explicit file, so they work from any working directory:

```bash
compose=(docker compose -f "$root/compose.yaml")
case "${1:-}" in
  build)     exec "${compose[@]}" build cli ;;
  dashboard) shift; exec "${compose[@]}" --profile dashboard up dashboard "$@" ;;
  shell)     exec "${compose[@]}" run --rm --entrypoint bash cli ;;
  fetch)     shift; exec "${compose[@]}" run --rm --entrypoint python cli scripts/fetch_data.py --auto "$@" ;;
  --entrypoint) ep="$2"; shift 2; exec "${compose[@]}" run --rm --entrypoint "$ep" cli "$@" ;;
  *)         exec "${compose[@]}" run --rm cli "$@" ;;
esac
```

The PowerShell version mirrors this, keeping the quote-safe `$Root` handling for the path with spaces and an apostrophe. `docker compose run` containers carry the `com.docker.compose.project=arcsv2` label, so Docker Desktop groups them under **arcsv2**.

### 3.3 Devcontainer

```json
{
  "name": "arcsv2",
  "dockerComposeFile": ["../compose.yaml"],
  "service": "dev",
  "runServices": ["dev"],
  "workspaceFolder": "/work",
  "shutdownAction": "stopCompose",
  "overrideCommand": false,
  "postCreateCommand": "pip install -e .[dev] && pytest -q"
}
```

The `dev` service is behind a profile. If Cursor's devcontainer version ignores profiles for `runServices`, drop `profiles` from `dev` only.

### 3.4 Dockerfile and `.dockerignore`

- Add `LABEL org.opencontainers.image.title="arcsv2" org.opencontainers.image.source="<repo url>"`.
- Extend `.dockerignore` with: `pilot/`, `pilot-large/`, `haps/`, `labels/`, `results/`, `work/`, `data/`, `target/`, `.snakemake/`, `ref.fa`, `*.fa`, `*.fa.gz`, `*.fasta.gz`, `*.gzi`, `*.sam`, `.devcontainer/`, `docs/reviews/`.
- Keep the image tag `arcsv2:dev` so CI's `docker run ... arcsv2:dev` steps keep working. CI may switch to `docker compose build cli`; it doesn't have to.

### 3.5 Acceptance

- `docker compose ls` shows `arcsv2`, and Docker Desktop groups the dev, dashboard and one-off containers under **arcsv2** only.
- `docker ps --filter label=com.docker.compose.project=arcsv2` lists every running arcsv2 container. The other projects' Compose groups contain none.
- `.\scripts\arcsv2.ps1 build`, `... dashboard`, `... shell`, `... fetch --dry-run --n-samples 2 --chroms chr20`, and `... pytest -q` via `--entrypoint pytest` all work from the repo root and from another folder.
- The build context drops by about 175 MB (`docker build` prints the context size).
- Update README, CROSS_PLATFORM.md and DASHBOARD.md to use the new commands.
